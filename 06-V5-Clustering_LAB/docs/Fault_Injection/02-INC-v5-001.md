# 🚨 INCIDENT TICKET — INC-v5-001

| Field | Detail |
|---|---|
| **INCIDENT ID** | INC-v5-001 |
| **SEVERITY** | 🔴 High |
| **TIME** | Reported following a routine network change window on one cluster member's host |
| **APPLICATION/SERVICE** | DigiStack Bank — Balance/Transaction Operations (cluster-wide) |

---

## 📉 Business Impact

Customers connecting to the application via **one specific host in the cluster** are unable to view their balance or complete transactions, while customers connecting via the other host continue to bank normally.

Because the cluster **load-balances across both members**, any given customer session may or may not be affected depending on which member happens to serve them — creating an **inconsistent, hard-to-reproduce complaint pattern** from the support desk's perspective:

> *"It works for me but not for my colleague on the same network."*

---

## 🧾 Customer / Business Symptom

- Some customers report the **Home page loads but shows a database connectivity warning** instead of the normal green status
- Others report the **Home page and login work fine**
- A subset of logged-in customers report their **account page fails to show a balance** or **rejects a deposit attempt outright**

## 🎫 Initial Alert / Ticket

Support desk escalation — **multiple tickets in a short window** describing inconsistent behavior for what should be the same application experience.

---

## ❗ Observed Error

- On **one host** in the cluster: the Home page status bar shows a **database error indicator** instead of "Connected"
- On the **other host**: everything functions normally
- **Both hosts** show the WAS server process itself as running and the application as **Started** in the cluster's admin view

---

## 🔍 Scope

One cluster member's ability to reach the database is affected; the other member is fully functional. The cluster itself (both server processes, node agents, DMgr) shows no errors — all report Started/Synchronized.

Login and session handling are unaffected on both members individually — the issue is specifically about **whichever member handles a database-dependent request**.

## ✅ NOT Affected

| Component | Status |
|---|---|
| DMgr | Reachable, cell configuration intact |
| Both Node Agents | Started |
| Cluster membership | Both members still shown as part of `devdsbinappcluster01`, both report application Started |
| Unaffected cluster member | Fully functional for Home, Login, Dashboard, Account, and transactions |
| PostgreSQL server on `dsb-db` | Confirmed running and accepting connections (verified from the database host itself and from the DMgr host) |

---

## 🕐 Recent Change

A **routine network-level change** was applied to one cluster member's host as part of a scheduled maintenance window shortly before the incident began.

> Exact nature of the change not detailed in the maintenance record beyond: *"outbound connectivity adjustment."*

---

## 📌 Starting Evidence

1. Home page via one member: Database status shows **error/warning**
2. Home page via the other member: Database status shows **Connected (green)**, fully normal
3. Both members: Admin Console shows **Started**, application **Started**, node **Synchronized**
4. Support tickets describe inconsistent experience matching a **roughly 50/50 pattern** consistent with load-balanced routing
5. PostgreSQL confirmed **running and reachable** from at least one other host in the environment
