# Generate plugin-cfg.xml
---

## Concept — What plugin-cfg.xml Actually Is

`plugin-cfg.xml` is a **routing table** in XML format, **generated by WAS, consumed by IHS**.

When a browser sends a request to IHS on port 80, the WAS plugin module (loaded into IHS) reads this file and decides:

> *"Does this URL pattern belong to a WAS application? If yes, which WAS server handles it, and on which port?"*

- If the URL **matches** → the plugin transparently forwards the request to WAS
- If it **does not match** (e.g. a static file request) → IHS handles it directly

The file contains entries like:

- Which WAS server(s) to route to (hostname + port)
- Which URI patterns are WAS-managed (e.g. `/digistack-bank/*`)
- Session affinity configuration (cookie vs URL rewriting)
- Connection timeout and retry settings

---

## Concept — Generated by WAS, Consumed by IHS

This is the **key architectural point**:

- **WAS generates** the file — because WAS knows its own topology (which applications are deployed, on which ports, with which URL patterns)
- **IHS consumes** the file — IHS cannot know this on its own

> ⚠️ The file is generated on the **WAS VM** and must be **physically copied to the IHS VM** (Sprint 4) before IHS can use it.

## Step 1 — Generate plugin-cfg.xml via Admin Console (GUI Method)

### Step 1.1 — Open the Admin Console

```
http://192.168.10.10:9060/ibm/console
```

Log in as `wasadmin`.

### Step 1.2 — Navigate to

```
Servers → Server Types → Web Servers
```

### Step 1.3 — Select webserver1

Click the **checkbox** next to `webserver1`.

### Step 1.4 — Click Generate Plug-in

Click **Generate Plug-in** from the button row above the table.

WAS generates the plugin configuration file. This takes **5 to 15 seconds**.

**Expected result — a success message at the top of the page:**

```
The plug-in configuration file was generated for webserver1.
```

### Step 1.5 — Note where WAS wrote the file

Navigate to:

```
Servers → Server Types → Web Servers → webserver1 → Plug-in Properties
```

Look at the **Plug-in configuration file name** field. It will show the path on the **dsb-dmgr** VM where the file was generated — something like:

```
/apps/IBM/WebSphere/AppServer/profiles/devdsbinappserver01/config/cells/devdsbincell01/nodes/devdsbinnode01/servers/webserver1/plugin-cfg.xml
```

## Step 3 — Inspect the Generated plugin-cfg.xml

### Step 3.1 — Confirm the file exists and check its size

```bash
ls -lh \
  /apps/IBM/WebSphere/AppServer/profiles/devdsbinappserver01/config/cells/devdsbincell01/nodes/devdsbinnode01/servers/webserver1/plugin-cfg.xml
```

**Expected result — file listed, typically 10 to 50 KB:**

```
-rw-r--r--. 1 root root XXK ... plugin-cfg.xml
```

### Step 3.2 — Confirm the WAS AppServer hostname is referenced

The plugin must know where to route requests — it should reference dsb-dmgr's IP or hostname:

```bash
grep -i "hostname\|ServerName" \
  /apps/IBM/WebSphere/AppServer/profiles/devdsbinappserver01/config/cells/devdsbincell01/nodes/devdsbinnode01/servers/webserver1/plugin-cfg.xml \
  | head -10
```

**Expected result — lines referencing `192.168.10.10` or `dsb-dmgr` as the WAS server hostname.**

### Step 3.3 — Confirm port 9080 is referenced

```bash
grep "9080" \
  /apps/IBM/WebSphere/AppServer/profiles/devdsbinappserver01/config/cells/devdsbincell01/nodes/devdsbinnode01/servers/webserver1/plugin-cfg.xml
```

**Expected result — at least one line referencing port `9080` — the standalone AppServer's HTTP port.**

> ✅ This confirms IHS will forward traffic to WAS on the correct port.

### Step 3.4 — Confirm the /digistack-bank context root appears

```bash
grep "digistack-bank" \
  /apps/IBM/WebSphere/AppServer/profiles/devdsbinappserver01/config/cells/devdsbincell01/nodes/devdsbinnode01/servers/webserver1/plugin-cfg.xml
```

**Expected result — one or more lines referencing `/digistack-bank` — confirming the plugin knows to route requests for your application to WAS.**

### Step 3.5 — Assign a shorter variable for the path

On **dsb-dmgr**:

```bash
PLUGIN_CFG=/apps/IBM/WebSphere/AppServer/profiles/devdsbinappserver01/config/cells/devdsbincell01/nodes/devdsbinnode01/servers/webserver1/plugin-cfg.xml

echo "Plugin config path set. File size:"
ls -lh $PLUGIN_CFG
```

### Step 3.6 — View the first 30 lines to understand the XML structure

```bash
head -30 $PLUGIN_CFG
```

**Expected result — XML content beginning with:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!--
  ...
-->
<Config ...>
    <Log .../>
    <Property .../>
    <Server .../>
    ...
```

## Concept — Key XML Elements in plugin-cfg.xml

| XML Element | Purpose |
|---|---|
| `<Server>` | Defines a WAS AppServer to route to — contains hostname and port 9080 |
| `<ServerCluster>` | Groups multiple servers for load balancing *(empty at v4.5 — only one server exists)* |
| `<UriGroup>` | Lists the URI patterns WAS handles — includes `/digistack-bank/*` |
| `<Route>` | Maps a UriGroup to a ServerCluster — ties URL patterns to backend servers |
| `<Log>` | Where the plugin writes its own log file on the IHS VM |

> **Note:** At v4.5 with a standalone AppServer, the `plugin-cfg.xml` is relatively simple — one server, one application, straightforward routing. At v8 (IHS cluster era), WAS regenerates this file to include **both cluster members and load-balancing weights**.
